01

Overview

What the platform is, and the two tracks of testing it manages side by side.

QA Automation Suite Runner is a self-hosted test management and automation platform. It runs as five Docker containers on a single Linux host and keeps two testing tracks in one place:

🧾 Manual track — TC Library & Test Cycles

Business-level test cases imported from Excel, organised by feature, assigned to testers, tracked to Pass/Fail/Blocked with a reason and linked Jira bugs.

🤖 Automation track — Scripts, Execution & Scheduling

Robot Framework + Selenium scripts, edited in a browser-based Monaco IDE, executed headless-in-Docker or watched live over noVNC, run ad-hoc, in suites, or on a cron schedule.

A TC Library item can be linked to an automation script — once linked, the Reports and Dashboard views can show results either "by script" or grouped by the real, business-named test case ("by test case"), and Excel exports include both.

How a test run flows through the system

  1. The UI calls the API to trigger a run (individual TC, a Suite, or a Schedule firing).
  2. The API enqueues a job on the BullMQ test-runs queue (Redis), then an in-process worker (runWorker.ts) picks it up.
  3. The worker dispatches each script to a runner container over plain HTTP, round-robining across runner instances when more than one is configured.
  4. The runner executes the script in a headless (or headed, VNC-visible) Chrome inside an Xvfb virtual display and streams log lines back.
  5. The API pushes live updates to the browser over Socket.io on the /runs namespace — events run:start, run:progress, run:log, run:complete — which is what powers the Execution page's live log and the Dashboard's running-jobs card.
  6. Final results, screenshots, videos and Robot Framework reports are written to Postgres and a shared artifacts volume.

Database Structure

One PostgreSQL database, one schema, everything scoped to a Project.

User and Project sit at the root. A Project is the tenant boundary — it owns almost everything else: environments, test cases, scripts, runs, suites, schedules, reports, the TC Library, and test cycles. ProjectMember joins a User to a Project with a per-project role.

ModelPurpose & key relationships

ScriptA Robot Framework file's content, belonging to one TestCase.
RunOne execution batch (status, trigger type MANUAL/SCHEDULED/INDIVIDUAL/GROUP/SUITE, sequential runSeq). Has many RunResults and an optional Report.
RunResultOne row per TestCase executed in a Run — status, duration, screenshot/video/RF-report/RF-log paths.
SuiteAn ordered set of "stages" (grouped by use-case tag, each sequential or parallel) for orchestrated multi-stage runs.
ScheduleA cron expression + TC list + environment, auto-triggering Runs.
ReportOne-to-one with a Run — summary text and a JSON analysis blob, optional emailed-at timestamp.
TcItemThe TC Library — business test cases imported from Excel (module/feature/title/steps/expected result). Optionally linked to a TestCase via linkedScriptId; feeds TestCycleItem.
TestCycleA manual regression pass — status PLANNING/ACTIVE/CLOSED, Jira label/JQL bug-discovery settings, optional Drive folder link. Deliberately separate from Suite.

Deploy to a Remote Linux Server

Build once on a Windows/Docker Desktop dev machine, package it, copy it across, install.

4.1 Prerequisites

  • Dev machine: Windows with Docker Desktop, PowerShell, and this repo checked out.
  • Target server: Linux with Docker Engine + the Compose plugin installed, and outbound network disabled/air-gapped is fine — nothing is fetched from the internet at install time.
  • Network access needed on the server: TCP 3000 (UI, must be reachable by users), TCP 6080 (noVNC live-browser view — only if you want to watch tests run live; otherwise it can stay bound to 127.0.0.1). Port 4000 (API) is intentionally bound to 127.0.0.1 only — the UI's Nginx reverse-proxies to it, so it never needs to be opened externally.

4.2 Package & copy

On the dev machine, build the images and run the packaging script:

# from the repo root
docker compose build
.\make-fresh-package.ps1 # -AdminEmail / -AdminName / -AdminPassword params override the defaults

This produces a self-contained fresh-deploy/ folder: Docker images saved as .tar files, the compose files, .env.example, Nginx config, a generated restore.sh installer, and a manifest.txt. Copy the whole folder to the server:

scp -r fresh-deploy/ user@server:/opt/qaasr/

4.3 Configure & install

ssh user@server
# on the server:
cd /opt/qaasr/fresh-deploy
cp config/.env.example config/.env
nano config/.env   # set real secrets — see below
chmod +x restore.sh
sudo ./restore.sh
Edit these in .env before running restore.sh:
  • POSTGRES_PASSWORD, REDIS_PASSWORD, JWT_SECRET, RUNNER_SECRET — generate with openssl rand -hex 32
  • VNC_HOST — leave as 127.0.0.1 for local-only, set to 0.0.0.0 to allow remote noVNC viewing on port 6080
  • SMTP_* — only needed if you want emailed reports
  • JIRA_HOST / JIRA_EMAIL / JIRA_API_TOKEN — only needed for Jira bug-linking in Test Cycles

restore.sh then, unattended: loads all five images, creates the named volumes for Postgres/scripts/artifacts data, starts Postgres and Redis and waits for them to be healthy, starts the API (Prisma migrations run automatically on boot) and polls its healthcheck, seeds the first SUPER_ADMIN user directly into the database, then brings up the UI and runner and prints the access URLs.

4.4 Post-install checklist

  • Open http://<server>:3000 and sign in with the seeded admin account.
  • Registration is closed by default. To onboard more users: set OPEN_REGISTRATION=true in .env, recreate the API container (docker compose up -d --force-recreate qaasr-api), have people register, then set it back to false and recreate again.
  • If you need noVNC reachable from outside the server, confirm the host firewall/security group allows inbound TCP 6080 — this is the single most common "it doesn't work" report post-deploy (see FAQ).

4.5 Updating later

For an application code change, rebuild and recreate the affected container(s) on the dev machine, save the new image, and load+recreate it on the server — the same docker save / scp / docker load / docker compose up -d --force-recreate <service> cycle used during development. There is no in-place auto-update.

Roles & Permission Matrix

Two independent role axes, resolved together on every request.

Global role — User.globalRole

SUPER_ADMIN ADMIN SUPER_USER STANDARD_USER

Applies platform-wide, independent of any one project.

Project role — ProjectMember.role

ADMIN SUPER_USER STANDARD_USER TEST_USER

Applies only within the project a user is a member of.

Precedence: a global SUPER_ADMIN or ADMIN bypasses every project-level check and every membership requirement — no ProjectMember row needed. Everyone else falls through to their actual project role. The one place SUPER_ADMIN and ADMIN diverge: User Management is SUPER_ADMIN-only — global ADMIN cannot manage other users.

06

Feature Guide

What each screen actually lets you do.

📋 TC Library Test Management

The business-level test case repository, grouped by Feature. This is where manual test cases live and where they get linked to automation.

  • Import Excel — bulk import with columns Test Case ID / Module / Feature / Title / Description / Steps / Expected Result / RF Script ID. A downloadable template is provided; the import summary reports new vs updated rows and any unmatched script IDs.
  • Automation status — each item is In Scope or Not Applicable (manual-only); toggling this changes what counts toward the automation coverage stats.
  • Link to Script — attach a TC to an existing automation script (individually or in bulk); linked items show a green "⚡ linked" badge, unlinked ones show "Unlinked".
  • Bulk actions: link/unlink, mark N/A or back In Scope, move to another feature, run linked scripts, add to a Test Cycle, delete.
  • Export the whole library to Excel.

📂 Script Library Automation

The automation side — generated Robot Framework scripts, grouped by use case. Easy to confuse with TC Library, but this is scripts, not business test cases.

  • Filter by type (UI/API/SIT) and status (Draft/Approved/Deprecated); drag-reorder within a use case.
  • Run a whole use-case group or a single script directly from the list.
  • Send to Execution pushes a selection over to the Execution page for a bigger run.
  • Export all, selected, or by use case, to Excel.

🧪 Test Cycle Test Management

A manual regression pass, deliberately separate from automation Suites — a snapshot of TC Library items assigned to testers and tracked to closure.

  • New Cycle — name, description, and optionally comma-separated Jira labels or a raw JQL query that auto-discovers related bugs.
  • Add test cases from the TC Library (feature-grouped picker), then assign each to a project member.
  • Record a result per item: Pass / Fail / In Progress / Blocked / Not Run. Fail and Blocked require a typed reason and can attach comma-separated Jira issue keys — that's the bug-linking mechanism.
  • Start / Close the cycle; a dedicated Bugs tab lists everything auto-discovered via labels/JQL, with a manual "Sync Now".
  • The Test Cycle Dashboard rolls all active cycles up into pass-rate stats, a status-by-cycle table, and a resource-wise (per-tester) summary.

📌 My Assignments

What a tester sees: every test case assigned to them across all cycles, grouped by cycle. Record a result directly from the row — Fail/Blocked expand an inline reason + Jira-key editor. Managers can switch to another tester's view via a Resource dropdown. A Daily Run History chart underneath shows pass/fail/blocked trend over 7–90 days, drillable to the individual runs of any day.

📊 Automation Dashboard

The automation-side overview: Total Test Cases / Automation Scope / Scripts Done / Automation % (with progress bar) / Automation Status (passed/failed/not-run) stat tiles; a Test Suites browser side-by-side with Recent Runs; a 7-day Pass/Fail trend chart; and a Flaky Tests card when any exist. Clicking into a suite run opens a full per-run dashboard with a By Script / By Test Case toggle and its own Excel export.

🖊️ Script Editor

A Monaco-based IDE for .robot files, with a project file tree and tabbed editing.

  • Import Script — link to an existing TC or import standalone; Import Folder bulk-imports a whole use case.
  • Project-wide content search, and F12 / Ctrl+Click go-to-definition on keywords, with hover previews.
  • Run executes headless inside Docker; Run in Host Browser does the same but opens a live noVNC view so you watch the browser drive in real time.

▶️ Execution

The run console. Select individual test cases or whole use-case groups from a checklist, set the Workers stepper, and hit Run. A horizontally-scrollable strip of Running Jobs cards sits above the Live Execution Log, which streams colour-coded pass/fail/warn lines in real time with an elapsed timer and a Stop button.

⏰ Scheduler

Suites, ad-hoc Quick Runs, and recurring cron Schedules, all in one place.

  • New Suite — build an ordered list of stages (one per use case), each toggled Sequential or Parallel.
  • The Threads stepper and Video toggle next to the Suites list set the parallel-worker count and recording for that suite's Quick Run.
  • Quick Run — a one-off run against a chosen environment, from a saved Suite or a hand-picked TC list.
  • New Schedule — Daily / Weekdays / Weekly / Monthly / Hourly / raw cron, an environment, a TC source, email recipients, and a recording toggle. Each schedule can also be triggered ad-hoc with "Run Now".

📈 Reports

Run history with stat tiles (total runs, average pass rate, flaky tests, average run time), a trend chart, and an expandable per-run list — each run shows pass/fail/skip counts, a Retry action, and downloadable per-script results with screenshots/video/RF logs. A sidebar tracks flaky tests and configures automated email reports.

Controlling Parallelism ("Threads")

Two knobs that look similar but do different things.

The Threads / Workers stepper (Scheduler & Execution pages)

This sets parallelWorkers for a suite run or a manual selection — how many test cases that specific run tries to execute at once. It's shared between the Scheduler's "Threads" control and the Execution page's "Workers" control via the same setting, so changing it in one place carries over to the other.

Keep it at 8 or below. The stepper UI allows up to 16, but the API validates and rejects any request above 8 — values of 9–16 will fail with an error when you try to run.

RUNNER_CONCURRENCY — the real physical ceiling

Set in .env (default 4), this controls how many parallel virtual displays (Xvfb) one runner container makes available — one display per test case actually executing at once inside that container. If every display is busy, the runner returns "all slots busy" and the request queues. The Threads/Workers value only matters up to however many slots RUNNER_CONCURRENCY actually provides — raising the stepper past that number just means requests wait for a free slot rather than truly running in parallel.

Each slot uses roughly 400–700 MB RAM under load, so size RUNNER_CONCURRENCY to the host's available memory, not just CPU count.

08

Scaling Runner Instances

More runner containers, not just more slots in one.

When one runner's RUNNER_CONCURRENCY ceiling isn't enough — you need more total parallel capacity across the whole system — add more runner containers with RUNNER_REPLICAS:

# edit .env
RUNNER_REPLICAS=3
RUNNER_CONCURRENCY=4      # applies to each replica

# regenerate the compose override and apply it
./gen-compose-override.sh
docker compose up -d

# verify
docker ps --filter "name=qaasr-runner"

This spins up qaasr-runner-1 … qaasr-runner-N, each with its own noVNC port (6081, 6082, …), and disables the original single qaasr-runner service. The API itself round-robins new work across all of them — there is no separate load balancer; total system-wide parallel capacity is simply:

RUNNER_REPLICAS × RUNNER_CONCURRENCY = total parallel test slots

For example, 3 replicas × 4 concurrency = 12 tests running simultaneously across the whole platform.

Troubleshooting & FAQ

Real issues encountered running this platform, and how they were actually resolved.

"Registration is disabled. Contact your administrator." — how do I add a new user?

Registration is closed by design (OPEN_REGISTRATION=false). Set it to true in .env, recreate the API container so it picks up the change (docker compose up -d --force-recreate qaasr-api — a plain restart won't reload the env file), have the person register, then set it back to false and recreate the container again to close it.

I lost the admin password / need to create the very first admin — there's no self-service way to become an admin

There is no bootstrap admin seed beyond the one created at install time, and no in-app "promote to admin" action. Temporarily open registration (above), register a new account, then promote it directly in the database:

docker exec -it qaasr-postgres psql -U <user> -d <db> \
  -c "UPDATE \"User\" SET \"globalRole\"='SUPER_ADMIN' WHERE email='you@example.com';"

Close registration again afterwards.

docker compose up fails: "container name already in use"

Usually means a previous deployment's containers are still running under a different Compose project name (Compose derives the project name from the current directory unless pinned). Check where the running container actually came from before touching anything:

docker inspect <container> --format '{{index .Config.Labels "com.docker.compose.project"}}'

If it's genuinely stale and there's no data to lose, stop and remove the old containers, then bring the new stack up.

The noVNC "watch tests run live" page won't load, or times out

Two very different causes, so diagnose in order:

  1. Check the runner container itself — docker logs qaasr-runner. If you see an x11vnc "Address already in use" crash, the VNC process is failing to bind (an application-level bug, already fixed in the current version's startup script).
  2. If the app-level check is clean, confirm it's reachable at all: curl -v http://localhost:6080/vnc.html from the server itself. If that succeeds but your browser still can't connect, it's a network/firewall block between your machine and the server (or a VDI egress policy blocking that specific port) — not an application bug. Compare against a port you know works (e.g. 3000) using the same test from your machine to isolate it.
The Script Editor is stuck on "Loading" and never shows the code

The Monaco editor's assets were historically fetched from a public CDN at runtime — on networks where a firewall silently drops that CDN's traffic, the editor hangs forever with no visible error. The current version bundles Monaco directly into the app so it never depends on any CDN. If this resurfaces after a custom build, check for a reintroduced CDN dependency in the editor's loader configuration.

I hot-patched a file into a running container but the fix doesn't seem to be applied

docker cp-ing a changed file into a container running a file-watcher (like tsx watch) can silently stop triggering restarts after repeated copies. Don't assume the copy worked — check the container logs or directly test the affected behaviour afterward. For anything beyond a trivial one-file fix, rebuild the image properly instead.

A Suite run fails immediately with a 400 error

Almost always stale data inside an old Suite definition — one of its saved test cases was deleted or its script changed since the suite was built. Recreate the suite (or re-add the affected stage) rather than debugging the old one.

An automation script fails with a path error like \\?\ or backslash-in-path

That prefix is a Windows-only long-path convention that has no meaning on the Linux runner — the script (or whatever generated it) assumed a Windows execution environment. Replace hardcoded Windows-style paths with Robot Framework's own OS-aware separator, ${/}, or a plain forward-slash join.

I set the Threads stepper above 8 and the run won't start

The stepper UI permits up to 16, but the API caps parallelWorkers at 8 and rejects anything higher. Keep it at 8 or below — see Controlling Parallelism.

Where do I open ports, and which ones actually matter?

Only two ports are ever meant to be reached from outside the server: 3000 (the UI — always needed) and 6080 (noVNC live-browser view — only if you want people to watch tests run live). The API (4000), Postgres and Redis are intentionally not exposed beyond the Docker network / localhost and never need a firewall rule.
